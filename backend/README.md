# Backend

## Overview
The backend folder has two runtime services:
- `api/`: FastAPI service used by the web app for auth, meetings, transcript, chat, and analytics APIs
- `agent/`: Python assistant runner that attaches to active meetings and handles transcript-driven assistant behavior

Both services use Redis as a shared event/state layer for meeting-time workflows.

## Backend Structure
- `backend/api/`
  - FastAPI app entry: `api/app/main.py`
  - modules: `app/modules/*` (`meetings`, `transcripts`, `chat`, `auth`, `analytics`, `join`, `stream_tokens`)
  - DB models/session: `app/db/models.py`, `app/db/session.py`
  - startup tasks: `app/core/startup_tasks.py`
- `backend/agent/`
  - runner entry: `agent/main.py`
  - manager/orchestration: `agent/manager/agent_manager.py`
  - stream agent factory and handlers: `agent/stream/stream_agent_factory.py`, `agent/stream/stream_event_handlers.py`
  - assistant core logic: `agent/core/*`

## API Service (FastAPI)
### Responsibilities
- user auth and refresh token routes
- meeting create/query/share/schedule/join/end flows
- transcript ingestion (webhook) and transcript websocket
- chat websocket and assistant chat message endpoint
- analytics reads and lifecycle-related updates

### Key Data Paths
1. **Meeting flow**
   - create meeting (`meetings` routes/services)
   - join by code/passcode (`join` module)
   - run meeting with websocket channels

2. **Transcript flow**
   - transcript webhook receives caption events
   - events queued to Redis (`transcript_events`)
   - worker consumes events and applies stabilization + dedupe
   - committed segments are stored and streamed via transcript websocket

3. **Chat flow**
   - incoming chat messages received over chat websocket
   - messages stored in Redis meeting chat list
   - fanout broadcast to connected meeting sockets

### Storage Used
- PostgreSQL tables (from `app/db/models.py`):
  - `users`
  - `meetings`
  - `meeting_analytics`
  - `meeting_participant_stats`
  - `processed_segments`
- Redis:
  - transcript queue/state keys
  - chat message buffers
  - websocket/rate-limit support keys

## Agent Service (Python)
### Responsibilities
- listen to Redis pub/sub meeting events
- attach assistant agent to active meetings
- process transcript events while call is active
- post assistant responses through API/chat path
- detach and clean up when meeting ends or assistant is disabled

### Runtime Flow
1. `agent/main.py` starts `AgentManager`.
2. `AgentManager` opens Redis and listens to:
   - meeting created
   - meeting ended
   - meeting snapshot
   - assistant preference updates
3. For each active meeting, manager creates a meeting agent via stream factory.
4. Stream event handlers forward transcript/user events to assistant core.
5. Manager detaches agents and releases resources on shutdown or meeting end.

## API and Agent Interaction
- FastAPI publishes meeting lifecycle events.
- Agent consumes lifecycle events and joins/leaves corresponding meetings.
- Assistant output is surfaced to users through existing meeting chat channels.
- Transcript context generated by API pipeline is used by assistant logic.

## Local Run Notes
- Run `backend/api` and `backend/agent` as separate processes.
- Both require environment variables for API URL, Redis, database and stream integrations.
